\begin{abstract}
Este trabajo compara tres formas de enviar la información de un control físico (cuatro pulsadores y un potenciómetro conectados a un Arduino Uno) a un juego de secuencias hecho en Unity. Los tres protocolos son texto separado por comas (CSV), JSON y mensajes binarios con verificación CRC. Los tres envían los mismos datos y usan el mismo programa en el Arduino; solo cambia la manera de escribir cada mensaje. Se comparan el tamaño del mensaje, la rapidez de respuesta, la cantidad de mensajes por segundo, el tiempo que Unity tarda en interpretarlos y la capacidad de cada uno para detectar errores. El binario fue el más rápido, con un tiempo de ida y vuelta promedio de 4,1\,ms y 969 mensajes por segundo, seguido de CSV (5,6\,ms y 490) y JSON (9,0\,ms y 200). Con una tasa de error de bit de 0,002, solo CSV dejó pasar mensajes dañados (0,13\,\%). Ninguno perdió mensajes y, al jugar, no se percibió diferencia entre ellos. Se recomienda el binario con CRC-16 para el control del vehículo y CSV como modo de depuración.
\end{abstract}

\begin{abstract}
This work compares three ways of sending the data of a physical controller (four push buttons and a potentiometer connected to an Arduino Uno) to a sequence game built in Unity. The protocols are comma-separated text (CSV), JSON, and binary messages with CRC verification. All three carry the same data and run on the same Arduino program; only the way each message is written changes. The comparison covers message size, response time, messages per second, the time Unity needs to read them, and how well each one detects errors. The binary protocol was the fastest, with an average round-trip time of 4.1\,ms and 969 messages per second, followed by CSV (5.6\,ms and 490) and JSON (9.0\,ms and 200). With a bit error rate of 0.002, only CSV let corrupted messages through (0.13\,\%). None lost messages and, when playing, no difference between them was noticed. The binary protocol with CRC-16 is recommended for vehicle control, with CSV as a debugging mode.
\end{abstract}}

\section{Introducción}

\IEEEPARstart{E}{n} un juego con control físico, el Arduino debe avisarle a Unity cada pulsación y cada giro del potenciómetro, rápido y sin errores. Esa información viaja por un cable serial como una fila de bytes, y hay varias maneras de ordenarla. El circuito utilizado para los tres casos es el mismo, conformado por cuatro pulsadores y un potenciómetro, Implementados en el mismo juego, solo cambiando la manera de escribir los mensajes. Esto nos permite tener argumentos fundamentados para la elección de protocolos en futuras entregas.

\section{Objetivos}

\subsection{Objetivo general}
Implementar y comparar experimentalmente distintos protocolos de comunicación entre un microcontrolador Arduino y un entorno interactivo en Unity, analizando el flujo de información entre el controlador físico y el simulador digital, para establecer criterios técnicos de selección del protocolo de transmisión de datos.

\subsection{Objetivos específicos}
\begin{itemize}
    \item Diseñar e implementar un circuito con Arduino que capture entradas digitales y analógicas.
    \item Investigar y aplicar estándares de construcción de paquetes (\emph{framing}), representación JSON y métodos de verificación de integridad.
    \item Desarrollar tres implementaciones de protocolo serial entre Arduino y Unity, justificadas desde el marco teórico.
    \item Conectar cada implementación con el simulador asignado (S3) y evaluar su comportamiento en uso real.
    \item Comparar cuantitativa y cualitativamente las implementaciones en latencia, legibilidad, tamaño, mensajes por segundo, costo de interpretación y robustez.
\end{itemize}

\section{Marco teórico}

\subsection{Cómo se arma un mensaje (framing)}
Por un cable serial los datos llegan como una fila continua de bytes, sin indicar dónde empieza ni dónde termina cada mensaje. Por eso se necesita un formato que marque esos límites, conocido como \emph{framing} \cite{tanenbaum}. Hay dos estrategias básicas:

\begin{itemize}
    \item \textbf{Un carácter que marca el límite.} Un byte reservado indica el fin (o el inicio) del mensaje. Por ejemplo, el salto de línea en protocolos de texto como NMEA 0183 \cite{nmea}, o el byte \texttt{0x7E} en HDLC y PPP \cite{rfc1662}. Es sencillo y, si algo falla, el receptor se vuelve a sincronizar en el siguiente límite. Su condición es que ese carácter no aparezca dentro de los datos.
    \item \textbf{Un campo con la longitud.} Al inicio del mensaje se indica cuántos bytes siguen. Sirve para datos de cualquier valor, pero si ese campo se daña el receptor se desorienta. Por eso suele combinarse con un marcador de inicio y un código de verificación.
\end{itemize}

El \textbf{encabezado} (\emph{header}) reúne los datos de control del mensaje, como el marcador de inicio, el tipo y la longitud. Así el receptor puede comprobar el mensaje antes de usar su contenido.

En los mensajes binarios, cualquier valor de los datos puede coincidir con el carácter de límite. Hay tres maneras de evitarlo:
\begin{itemize}
    \item \textbf{Byte stuffing (escape de bytes).} HDLC y PPP reemplazan cada \texttt{0x7E} o \texttt{0x7D} que aparezca en los datos por dos bytes: \texttt{0x7D} (un aviso) seguido del byte original con sus bits invertidos mediante XOR con \texttt{0x20} \cite{rfc1662}. SLIP usa la misma idea con otros valores \cite{rfc1055}. Su costo es que el mensaje puede crecer; en el peor caso, se duplica.
    \item \textbf{COBS} (\emph{Consistent Overhead Byte Stuffing}). Evita el byte reservado con un aumento máximo de 1 byte por cada 254 \cite{cobs}.
    \item \textbf{Restringir los caracteres.} En los protocolos de texto basta con usar solo dígitos y separadores, de modo que el salto de línea nunca forma parte de los datos.
\end{itemize}

\subsection{JSON y su lectura en C\#/Unity}
JSON es un formato de texto para intercambiar datos, definido en el RFC 8259 y en ECMA-404 \cite{rfc8259}, \cite{ecma404}. Organiza la información en pares nombre--valor, listas, números y textos. Se puede leer a simple vista y casi todos los lenguajes lo soportan. Su desventaja es que los nombres de los campos se repiten en cada mensaje y los números se escriben como texto, así que ocupa más bytes.

En Unity hay dos opciones habituales para leerlo:
\begin{itemize}
    \item \textbf{\texttt{JsonUtility}} \cite{unityjson}. Viene incluida en Unity y es rápida y ligera. Solo lee campos públicos o marcados con \texttt{[SerializeField]}, en clases marcadas con \texttt{[Serializable]}; no lee propiedades. No admite diccionarios ni listas como raíz del documento, y no distingue un campo ausente de uno con valor por defecto.
    \item \textbf{Newtonsoft Json.NET} \cite{newtonsoft}, disponible como paquete de Unity. Es mucho más flexible (propiedades, diccionarios, atributos de mapeo), pero usa más memoria, tarda más por mensaje y en algunas plataformas necesita configuración adicional.
\end{itemize}

\subsection{Verificación de integridad}
Para saber si un mensaje llegó dañado, el emisor agrega un valor calculado a partir de los datos y el receptor lo recalcula; si no coinciden, descarta el mensaje. La Tabla~\ref{tab:integridad} resume los métodos considerados. Un CRC es un cálculo basado en una división matemática especial entre polinomios \cite{peterson}, \cite{williams}. \section{Metodología y desarrollo}

\subsection{Circuito}
Se usó un Arduino Uno R3 (Figs.~\ref{fig:circuito} y~\ref{fig:arduino-conectado}) con estas conexiones:
\begin{itemize}
    \item \textbf{Pulsadores:} B1 en D7, B2 en D6, B3 en D4 y B4 en D5. Cada uno va entre el pin y GND, y usa la resistencia interna del Arduino (\texttt{INPUT\_PULLUP}); al presionarlo, el pin lee \texttt{LOW}.
    \item \textbf{Potenciómetro de 1\,k$\Omega$:} los extremos a 5\,V y GND, y el cursor en A0 (valores de 0 a 1023).
\end{itemize}
El programa del Arduino ignora los rebotes de los pulsadores durante 20\,ms y nunca se queda esperando con \texttt{delay()}; mide el tiempo con \texttt{millis()} para no bloquear el puerto serial. Envía un mensaje cada 20\,ms (50 por segundo) y otro de inmediato cuando cambia un pulsador. El programa \texttt{CircuitTest} sirve para comprobar el montaje, porque muestra el estado de los pulsadores y del potenciómetro en texto.

\subsection{Protocolos implementados y justificación}
La Tabla~\ref{tab:protocolos} resume las tres implementaciones. Se eligieron para cubrir tres puntos distintos entre legibilidad y eficiencia:
\begin{itemize}
    \item \textbf{CSV} es el más simple y fácil de leer. Cada mensaje es una línea de texto con valores separados por comas y termina en salto de línea. No necesita escape de bytes, porque solo usa dígitos, comas y el signo \texttt{*}. Para verificar integridad usa un XOR de 8 bits escrito en hexadecimal, al estilo NMEA \cite{nmea}.
    \item \textbf{JSON} es un formato estructurado y extensible, muy usado en la industria \cite{rfc8259}. Escrito en una sola línea no contiene saltos de línea internos, así que tampoco necesita escape. Para verificar integridad usa la suma módulo 256 de los 7 bytes del estado.
    \item \textbf{Binario} es el más compacto y el más robusto. Es el único que debe resolver el problema del escape de bytes. Cada mensaje empieza con el marcador \texttt{0x7E}, sigue con la longitud, el tipo y los 7 bytes del estado, y termina con un CRC-16/CCITT-FALSE (polinomio \texttt{0x1021}, valor inicial \texttt{0xFFFF}). Todo lo que sigue al marcador se escapa con el esquema HDLC \cite{rfc1662}.
\end{itemize}
Además, cada protocolo usa un método de integridad distinto (XOR, suma y CRC). Así, la prueba de errores permite comprobar en la práctica lo que predice la teoría.

En Unity, un hilo aparte lee el puerto con \texttt{System.IO.Ports.SerialPort} y entrega los bytes al decodificador uno por uno. Así nunca se supone que un mensaje llega completo en una sola lectura. El hilo anota la hora de llegada de cada mensaje y lo guarda en una cola; en cada cuadro del juego, el hilo principal toma todos los mensajes pendientes. Si el puerto se desconecta o llega un mensaje dañado, el error se cuenta y el juego sigue funcionando.

\subsection{Procedimiento de medición}
Todas las pruebas usan el mismo montaje: Arduino Uno R3 a 115200 baudios (formato 8N1, 10 bits por byte), un mensaje cada 20\,ms, filtro de rebotes de 20\,ms y Unity 6000.0.82f1 en modo Play del editor. Equipo de medición: portátil con procesador AMD Ryzen 5 5500U, 16\,GB de RAM y Windows 10, con el Arduino conectado directamente a un puerto USB del equipo, sin hub (puerto COM4). Como los tres protocolos salen del mismo programa (\texttt{SerialController}) y Unity elige cuál usar con \texttt{M<n>}, cualquier diferencia se debe a la forma del mensaje.

Para cada protocolo (CSV, JSON y binario) se cierra el Monitor Serial, se conecta Unity al puerto, se elige el protocolo y se pulsa \emph{Full run}. En unos 45\,s, sin tocar los controles, se ejecutan cuatro pruebas y se guarda una fila en \texttt{Measurements/summary.csv}:
\begin{enumerate}
    \item \textbf{Valor de prueba.} Unity envía \texttt{T} y el Arduino responde un valor fijo (\texttt{seq=32126}, \texttt{b=[0,1,0,1]}, \texttt{pot=638}, \texttt{echo=125}). Sus bytes incluyen \texttt{0x7E} y \texttt{0x7D}, así que también se comprueba el escape de bytes.
    \item \textbf{Tiempo de ida y vuelta (RTT).} Unity envía 500 pings (\texttt{P<id>}), uno cada 20\,ms, y mide cuánto tarda en volver cada \texttt{echo}. Se reportan promedio, mediana, percentil 95, mínimo, máximo y desviación estándar.
    \item \textbf{Máximo de mensajes por segundo.} Con \texttt{R0}, el Arduino transmite sin pausa durante 5\,s. Se cuentan mensajes y bytes por segundo, mensajes perdidos (saltos en \texttt{seq}) y errores.
    \item \textbf{Errores.} El cable USB casi nunca falla, así que durante 15\,s Unity invierte al azar cada bit recibido con probabilidad 0,002 antes de decodificarlo. Interesa qué porcentaje de mensajes dañados el protocolo acepta sin darse cuenta.
\end{enumerate}

Se espera que el RTT dependa de dos cosas: los bytes de la respuesta (cada uno tarda unos 87\,$\mu$s en el cable) y el tiempo que Unity tarda en interpretarla. Lo demás (USB, Arduino, sistema operativo) es igual para los tres. Del mismo modo, el máximo teórico de mensajes por segundo sale de dividir los 11\,520 bytes por segundo del cable entre el largo del mensaje.

La legibilidad se evalúa con los bytes por mensaje, la parte que es dato útil (siempre los mismos 7 bytes) frente al relleno, si se puede leer en el Monitor Serial y una valoración cualitativa de cuatro tareas: leer el estado, depurar un error, agregar un campo y escribir el decodificador.

\subsection{Simulador asignado: S3 -- Juego de secuencias}
El juego muestra una secuencia creciente de casillas de colores con tonos, y el jugador debe repetirla con los pulsadores B1 a B4. El potenciómetro ajusta el tempo: el tiempo entre pasos de la secuencia va de 0,90\,s a 0,22\,s, y el tiempo para responder, de 5\,s a 2\,s. Para interpretar los resultados importan tres ideas:
\begin{enumerate}
    \item \textbf{Cada pulsación es un evento único.} Perderla o repetirla hace fallar la partida aunque el jugador haya acertado. Por eso importa más no perder mensajes (se vigila con \texttt{seq}) que enviar muchos por segundo. El Arduino envía un mensaje apenas cambia un pulsador, y Unity revisa todos los mensajes recibidos en cada cuadro del juego.
    \item \textbf{La latencia de los pulsadores se nota} en la respuesta visual y sonora, sobre todo con el tempo más rápido (0,22\,s por paso).
    \item \textbf{El potenciómetro cambia despacio}, así que tolera una latencia mayor.
\end{enumerate}
Por eso el S3 exige poco ancho de banda, pero es muy sensible a la pérdida de eventos.

\section{Análisis y discusión}

El tamaño del mensaje explica casi todo lo que se midió: cuanto más corto, más mensajes caben en el cable y menos tarda cada respuesta.

\textbf{Mensajes por segundo.} El cable mueve 11\,520 bytes por segundo, así que el largo del mensaje fija el límite. El binario llegó a 969 mensajes por segundo, casi el doble que CSV (490) y 4,8 veces más que JSON (200). Los valores medidos quedaron a un 2\,\% del máximo teórico, de modo que ni el Arduino ni Unity fueron el cuello de botella (Fig.~\ref{fig:throughput}).

\textbf{Latencia.} Cada byte adicional suma unos 87\,$\mu$s. Con 34 bytes más, JSON debía tardar 3,0\,ms más que CSV; tardó 3,4\,ms. El binario, con 11 bytes menos, debía ahorrar 1,0\,ms y ahorró 1,4\,ms (Fig.~\ref{fig:latencia}). El peor caso (percentil 95 de JSON, 12,1\,ms) queda por debajo de un cuadro a 60\,FPS (16,7\,ms) y muy lejos de los 220\,ms mínimos entre pasos del juego.

\textbf{Interpretación.} Leer un mensaje cuesta menos de 1\,$\mu$s en binario, unos 62\,$\mu$s en CSV y unos 121\,$\mu$s en JSON (Fig.~\ref{fig:deserializacion}). La diferencia es la conversión de texto a números, que el binario no necesita. Aun así, JSON usa menos del 1\,\% de un cuadro. El retardo hasta que el juego usa el mensaje fue igual en los tres (3,0 a 3,2\,ms), porque depende del ritmo del juego y no del protocolo.

\textbf{Robustez.} Con una tasa de error de bit de 0,002 (Fig.~\ref{fig:robustez}):
\begin{itemize}
    \item CSV aceptó 3 mensajes dañados de 2271 (0,13\,\%); JSON y binario, ninguno.
    \item El XOR de CSV y el CRC del binario detectaron entre el 88 y el 89\,\% de los errores; el resto se descartó por formato roto.
    \item En JSON la suma detectó solo el 5\,\% (90 de 1821). El 95\,\% restante se descartó porque el texto dejó de ser JSON válido: su robustez viene del formato, no de la suma.
    \item Con unos 2000 mensajes dañados por prueba no se distingue el CRC-16 de la suma. La teoría predice un error no detectado cada 65\,536, fuera del alcance de esta prueba.
\end{itemize}
Además, JSON aceptó menos mensajes (1282) que CSV (4701) o binario (7886), porque con la misma tasa de error un mensaje largo se daña con más frecuencia.

\textbf{Legibilidad.} CSV y JSON se leen en el Monitor Serial. El binario necesita herramientas, como el visor de la última trama en Unity o el script \texttt{Tools/protocol\_reference.py}.

\textbf{Para el S3.} No se perdió ningún mensaje y la latencia máxima (14,5\,ms) es pequeña frente al juego. Los tres protocolos sirven, así que la elección depende de la depuración y de la facilidad para ampliar el sistema, no de la rapidez.

\section{Conclusiones}
Los tres protocolos transmitieron correctamente el estado del control, ninguno perdió mensajes y, al jugar, no se notó diferencia entre ellos. Esto es coherente con los datos: la latencia máxima medida (14,5\,ms) es muy pequeña frente al tiempo entre pasos del juego (0,22\,s o más). Para el S3, la rapidez no decide la elección.

Las diferencias aparecen en otros aspectos:
\begin{itemize}
    \item \textbf{Tamaño.} El binario usa 12 bytes por mensaje, frente a 23 de CSV y 58 de JSON. Por eso permite casi el doble de mensajes por segundo que CSV y unas 4,8 veces más que JSON. A 50 mensajes por segundo, JSON ocupa cerca de la cuarta parte del cable solo con el estado actual (2914 de 11\,520 bytes por segundo), y el binario, cerca del 5\,\%.
    \item \textbf{Robustez.} Solo CSV aceptó mensajes dañados. El CRC y el XOR detectaron casi nueve de cada diez errores; en JSON, el 95\,\% se descartó por el formato y no por la suma de verificación.
    \item \textbf{Legibilidad.} CSV y JSON se leen a simple vista; el binario exige herramientas y más trabajo para modificarlo.
\end{itemize}

Para el Corte~2 (vehículo) se recomienda el binario con CRC-16. Se agregarán más sensores, y con un formato de texto cada dato nuevo alarga el mensaje; además, los motores generan ruido eléctrico, y el CRC es la verificación más fiable de las tres. CSV queda como modo de depuración, porque transporta el mismo estado y se lee en el Monitor Serial. Para el proyecto final se mantiene la misma elección: el binario ocupa cerca del 5\,\% del cable con el estado actual, lo que deja ancho de banda libre para los sensores que se sumen. JSON conviene si lo que más importa es agregar campos fácilmente y el volumen de datos es pequeño.

Estos resultados tienen límites. Cada protocolo se midió en una sola corrida y en un solo equipo, y los errores se simularon por software, sin el ruido real de motores. Con unos 2000 mensajes dañados por prueba no se puede distinguir el CRC-16 de la suma de JSON. Una prueba con el vehículo funcionando permitiría confirmar la ventaja del CRC.
